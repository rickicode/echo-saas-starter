# Plugin-based SaaS starter kit with Go/Echo backend and React frontend

A greenfield implementation delivering a modular SaaS starter kit. The backend uses Go with Echo, organized around a plugin registry that manages lifecycle (init, migrate, routes, shutdown). The frontend is a React SPA (TanStack Router, Tailwind) served via go:embed. Plugins cover auth (PASETO v4), RBAC roles, user management, subscription plans, and a docs CMS. SQLite and PostgreSQL are interchangeable via a URL-scheme-based factory.

**Watch for:** Password comparison uses a byte-by-byte loop instead of `crypto/subtle.ConstantTimeCompare`, creating a timing side-channel (confirmed). The plugin removal guarantee partially holds but breaks at the import-graph level because roles, plans, users, and docs all import the `auth` package directly for `GetUserFromContext` and `RequireAuth` (confirmed). SQL migrations use `AUTOINCREMENT` and `INSERT OR IGNORE` syntax that won't run on PostgreSQL without modification (confirmed). The frontend `RequireRole` component doesn't actually check roles — it passes all authenticated users through (confirmed).

## High-level view

The plugin architecture draws a clean line between the core (interfaces, lifecycle manager, middleware) and individual feature plugins. Each plugin owns its migrations, routes, handlers, and repository. The dependency direction is strictly upward: plugins depend on `core`, and downstream plugins depend on `auth` and `roles` for their middleware. This means `auth` is a load-bearing foundation — you cannot remove it without breaking every other plugin. The claimed "delete a folder and a registry line" guarantee only works for the leaf plugins (plans, docs, users), not for auth or roles.

Auth is built on PASETO v4 local tokens with argon2id password hashing. The token flow includes refresh-token rotation (old token deleted before new one issued). The argon2id parameters (1 iteration, 64 MB, 4 threads) are OWASP-recommended. However, the password comparison function is vulnerable to timing attacks, and `PASETO_SECRET` has no minimum-length validation at startup — the system will fail at first token generation with an opaque error if the secret is too short.

The database layer uses `?` placeholders throughout, which works for SQLite but not for pgx (which expects `$1, $2, ...`). Combined with SQLite-specific DDL syntax (`AUTOINCREMENT`, `INTEGER PRIMARY KEY`, `INSERT OR IGNORE`, `ON CONFLICT ... DO UPDATE`), the PostgreSQL path is non-functional without a query translation layer or separate migration files. The architecture promises dual-database support but currently only delivers SQLite.

The frontend mirrors the plugin structure with `ui/src/plugins/` directories for auth, roles, plans, users, and docs. Type safety is maintained through explicit TypeScript interfaces for all API contracts. The token-refresh logic in `lib/api.ts` has a race condition: a 401 triggers a refresh and then throws an error expecting the caller to retry, but no retry actually happens — the request simply fails.

1. **Timing-unsafe password comparison** — `verifyPassword` in both `auth/handlers.go` and `users/handlers.go` uses a byte-by-byte loop. Replace with `crypto/subtle.ConstantTimeCompare`.
2. **PostgreSQL placeholder incompatibility** — All queries use `?` placeholders. pgx requires `$1, $2, ...`. Add a placeholder rewriter in the database layer or use separate query strings per driver.
3. **SQLite-only DDL in migrations** — `AUTOINCREMENT`, `INSERT OR IGNORE`, `BOOLEAN DEFAULT TRUE`, and `ON CONFLICT ... DO UPDATE` are SQLite syntax. PostgreSQL needs `SERIAL`/`GENERATED`, `INSERT ... ON CONFLICT DO NOTHING`, and `BOOLEAN DEFAULT true`.
4. **Frontend role guard is a no-op** — `RequireRole` component ignores the `roles` prop and passes all authenticated users. Either fetch user roles from the backend or enforce authorization server-side only and remove the misleading component.
5. **Token refresh doesn't retry the original request** — `handleResponse` in `lib/api.ts` refreshes the token on 401, then throws an error. The caller receives a failure even when refresh succeeds. Implement retry-after-refresh or use an interceptor pattern.
6. **PASETO secret not validated at startup** — If `PASETO_SECRET` is set but shorter than 32 bytes, the app boots fine but fails at first token generation. Validate length in `config.Load()`.
7. **Cross-plugin import coupling** — `roles`, `plans`, `users`, and `docs` all import `auth` directly for `GetUserFromContext` and `RequireAuth`. This prevents removing `auth` without compilation errors. Extract the middleware interface to `core` if true plugin independence is a goal.
8. **Avatar upload has no validation** — `UploadAvatar` accepts any file type and any size. Add content-type whitelist and size limit to prevent abuse.
9. **Hardcoded role_id=3 in registration** — The auth handler inserts `role_id=3` assuming it's the "user" role. If the roles plugin is removed or role IDs change, this silently fails (error is discarded with `_ =`).

## Timing-unsafe password comparison

Both `auth/handlers.go` and `users/handlers.go` contain identical `verifyPassword` functions that compare password hashes byte-by-byte:

```go
for i := range hash {
    if hash[i] != expectedHash[i] {
        return false
    }
}
```

This exits early on the first mismatched byte, leaking information about how many leading bytes match. The fix is one line: `return subtle.ConstantTimeCompare(hash, expectedHash) == 1`. The duplicated password-hashing code between the two packages is also a maintenance risk — a fix in one won't automatically propagate to the other. (confirmed)

## PostgreSQL is structurally unsupported despite the abstraction

The database factory correctly routes `postgres://` URLs to pgx and `sqlite://` URLs to modernc/sqlite. But the abstraction breaks at the query layer:

Every repository uses `?` as the placeholder. pgx requires positional `$1, $2, ...` syntax. The first query executed against PostgreSQL will fail with a syntax error. Additionally, the DDL migrations use SQLite idioms that have no PostgreSQL equivalents:

- `INTEGER PRIMARY KEY AUTOINCREMENT` → PostgreSQL needs `SERIAL PRIMARY KEY` or `GENERATED ALWAYS AS IDENTITY`
- `INSERT OR IGNORE` → PostgreSQL needs `INSERT ... ON CONFLICT DO NOTHING`
- `ON CONFLICT(user_id) DO UPDATE SET` → works in both, but only if the table is created with a proper unique constraint (which it is, via PRIMARY KEY)
- `BOOLEAN DEFAULT TRUE` with values `0`/`1` in queries → PostgreSQL `BOOLEAN` expects `true`/`false`

The `is_active = 1` and `is_active = 0` comparisons scattered throughout WHERE clauses will silently return wrong results on PostgreSQL if the column is a true boolean. (confirmed)

## Plugin isolation and the removal guarantee

The dependency graph:

```
core (interfaces)
  ├── auth (standalone)
  ├── roles → auth
  ├── users → auth, roles
  ├── plans → auth, roles
  └── docs → auth, roles
```

Removing `docs`, `plans`, or `users` requires deleting the folder and one line in `registry.go`. That compiles cleanly. Removing `roles` breaks `users`, `plans`, and `docs` (they import `roles.RequireRole`). Removing `auth` breaks everything.

The coupling is architectural: downstream plugins import `auth.RequireAuth`, `auth.GetUserFromContext`, and `roles.RequireRole` directly from the package. To make auth truly removable, these middleware functions and the context-user extraction would need to live in `core` as interfaces with the auth plugin providing the implementation. This is a deliberate trade-off (simplicity over full isolation), but it should be documented rather than promised as "delete and compile." (confirmed)

The hardcoded `role_id=3` in `auth/handlers.go` Register function creates a hidden coupling: `auth` writes to the `user_roles` table owned by the roles plugin. If the roles plugin isn't registered (and its migration doesn't run), this INSERT silently fails because the table doesn't exist and the error is discarded.

## Frontend token refresh race condition

In `lib/api.ts`:

```typescript
if (response.status === 401) {
    const refreshed = await attemptTokenRefresh()
    if (!refreshed) {
        // redirect to login
    }
    throw new Error('Token refreshed, retry request')
}
```

After a successful refresh, the function throws an error with message "Token refreshed, retry request". No caller catches this and retries — every call site treats thrown errors as failures. The user sees a transient error flash, then subsequent requests work (because the token was refreshed). This creates a poor UX where the first request after token expiry always fails visibly. (confirmed)

## Avatar upload without validation

`users/handlers.go` `UploadAvatar` reads any file from the multipart form, uses only the original extension to construct the filename, and writes it to disk with no checks:

- No content-type validation (a user can upload an executable with a `.jpg` extension)
- No file-size limit (defaults to Echo's 32MB body limit, which is large for an avatar)
- The filename is `{userID}{ext}`, preventing path traversal, but the extension is user-controlled
- Files are written to `./uploads/avatars/` relative to the working directory — this path isn't served by the SPA handler and there's no static file route registered for it

The uploaded avatars are unreachable via HTTP because no route serves the `/uploads/` directory. (confirmed)

## Migrations lack idempotency tracking

Every plugin runs all its migration files on every startup (`CREATE TABLE IF NOT EXISTS` prevents crashes). But there's no tracking of which migrations have already run. This means:

- `INSERT OR IGNORE` seed data re-executes every boot (harmless for idempotent seeds, but wasteful)
- If a future migration needs to ALTER a table, there's no way to skip it on subsequent runs without adding a migration-tracking table

This is acceptable for a starter kit, but it's worth noting that the migration approach doesn't scale past schema creation.

## Test coverage gaps

The test suite covers config loading, database factory selection, and PASETO token generation/validation. Not tested:

- Any HTTP handler (no integration tests for auth flows, role checks, plan assignment)
- The password hashing/verification functions
- SQLite database operations (the factory test creates a connection but doesn't exercise queries)
- The plugin manager lifecycle (init → migrate → routes → shutdown)
- Frontend: no tests present

For a starter kit meant to be extended, the absence of handler tests means there's no regression safety net when users modify the code.
